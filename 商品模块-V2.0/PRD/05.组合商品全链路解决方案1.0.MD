## 1. 项目背景

### 1.1 业务场景

商城存在"礼盒套装""福利用品包""节日组合装"等场景——一个可售商品由多个供应链子SKU组合而成（如"端午福利礼盒"= 蛋黄酥×2 + 碧螺春×1 + 坚果礼盒×1 + 礼盒包装×1 + 贺卡定制×1）。这类商品的核心特征是：

| 维度 | 普通商品 | 组合商品 |
|:---|:---|:---|
| SKU形态 | 单一SKU，独立存在 | 组合SKU = 主SKU + BOM清单（多个子SKU） |
| 供货来源 | 单一供应商/一品多商 | 每个BOM子项可能来自不同供应商 |
| 成本构成 | 供货价 = 单品采购价 | 供货价 = Σ(子项供货价 × 用量)，即聚合值 |
| 库存约束 | 单品库存 | 库存 = min(各子项库存 ÷ 用量)，瓶颈子项决定 |
| 供应商决策 | 按SKU级别指定 | 按BOM子项级别分别指定，逻辑与单品一致 |
| 履约方式 | 单一发货单 | 按供方拆单，分别发货 |

### 1.2 现状

商城现有商品体系仅支持单一SKU的选品、定价与履约。在实际企业福利业务中，"端午礼盒""福利用品包"等场景要求将一个可售商品拆解为多个供应链子SKU（BOM）的组合形态——各子项可能来自不同供应商、成本为聚合值、库存受瓶颈子项约束。新增有"组合套装/营销买赠"的类型枚举，但BOM编辑、聚合计算、供方推荐等能力尚未落地，商城运营平台的选品→定价→推品→异常处理全链路也尚未考虑组合商品的差异。

本次补丁以 **"核心业务逻辑与校验零改动，前端展示层按组合类型适配"** 为原则，将BOM复杂度闭环在供应链侧，对外输出标准SKU，使运营平台在选品、定价、异常处理等主流程中对组合商品无感知，同时通过商品详情页的组合供货弹窗支持子项级供方决策，并补齐组合订单按供方拆单履约的链路。

### 1.3 创建入口与部门分工

组合商品存在两条创建入口，创建后统一归口供应链侧闭环、输出标准SKU：

| 入口 | 操作端 | 说明 |
|:---|:---|:---|
| 供应链组建 | 供应链系统·组合商品管理 | 商品部/采购部用已入池的供应链SKU组建组合（本方案主链路） |
| 供应商发布申报 | 供应商后台·商品发布申请 | 供应商自建组合并申报（发布类型含实物/虚拟/组合），申报审核通过后入池；供应商端不单设组合菜单 |

```
销售部/运营部提出需求           商品部/采购部创建组合             运营部选品推品上架
┌──────────────┐         ┌──────────────────────┐         ┌──────────────────────┐
│              │         │                      │         │                      │
│ "需要端午礼盒" │ ──────→ │ ① 确定BOM子项+用量     │ ──────→ │ ② 从商品池加入选品清单  │
│ "需要福利用品包"│  需求输入  │ ② 逐子项指定默认供方(必填) │  输出标准  │                      │
│              │         │ ③ 标记优选(可选，非必填) │  SKU    │ ③ 定价推品页选渠道+定价 │
│              │         │ ④ 提交审批入池          │         │                      │
└──────────────┘         └──────────────────────┘         └──────────┬───────────┘
                                                                     │
                                          ┌──────────────────────────┘
                                          ▼
                                   ┌──────────────────────┐
                                   │                      │
                                   │ ④ 商品详情页Tab2      │
                                   │    [组合供货]弹窗       │
                                   │    逐子项确定最终供方    │
                                   │    可选优选/最低价/自选  │
                                   │                      │
                                   └──────────┬───────────┘
                                              │
                                    ┌─────────┴─────────┐
                                    ▼                   ▼
                              全部子项=优选          存在非优选
                              → 直通上架 ✅         → 待处理选品 ⚠️
```

| 部门 | 系统 | 职责 | 产出物 |
|:---|:---|:---|:---|
| **销售部/运营部** | 线下/口头 | 根据客户协议或者市场需求提出组合商品需求（礼盒主题、目标客群、预算范围等） | 组合商品需求描述 |
| **商品部/采购部** | 供应链系统 | ① 确定BOM结构（子SKU+用量）② 为子项指定供方（每个子项至少指定一个已准入供应商）③ 可选标记优选标签+推荐理由 ④ 提交审批入池 | 已审批的组合SKU（含供货价聚合值+优选标签） |
| **运营部** | 商城运营平台 | ① 从商品池加入选品清单 ② 定价推品页配置渠道+售价 ③ 商品详情页"组合供货"弹窗逐子项确定最终供方（可采用优选、切换最低价、或自选其他供方） ④ 保存推品 | 生效的商城SKU 或 待处理选品待办 |

**关键职能边界**：

| 边界 | 说明 |
|:---|:---|
| **商品部创建，运营部决策** | 商品部负责"搭出这个组合"（BOM+初步供方+推荐意见），运营部负责"决定最终卖给哪个渠道、用哪个供方、卖多少钱" |
| **优选标签是推荐** | 商品部标记的优选供方是专业推荐意见，运营部可以采用（直接豁免审批），也可以不采用（走指定审批流程）。优选标签不标记也完全允许——此时该子项进入"最低价优先"逻辑，运营可从任意准入供应商中选择 |
| **运营不替代供应链做采购** | 运营部在供应链已准入的供应商范围内做选择，不直接寻源、不谈判价格、不签采购合同 |

**关键拍板口径**：

| 事项 | 口径 |
|:---|:---|
| 上架边界 | 供应链负责BOM组建到审批入池（成为可被选品的标准SKU）；渠道定价与上架仍由运营平台决策，不迁入供应链 |
| 审批归属 | 组合商品审批在平台审批管理处理，不在组合商品管理页；供应链侧仅提交（草稿→待审批）/撤回/停用，审批通过后状态由平台回写为已发布 |
| 履约链路 | 组合套装/营销买赠均仅支持一件代发，不支持集采直发 |

## 2. 需求目的

### 2.1 要达成什么

| # | 目标 | 衡量标准 |
|---|------|---------|
| G1 | **核心业务逻辑与校验零改动** | 选品加入清单、定价推品校验、毛利红线、异常分流、渠道上下架等核心逻辑与普通SKU完全一致，不新增组合专属规则。前端展示层按组合类型做适配（列表筛选新增组合类型、详情页BOM子件清单、组合供货弹窗等） |
| G2 | **BOM复杂度供应链闭环** | 供货价聚合、库存瓶颈计算、优选标签判定全部在供应链侧完成，对外输出标准SKU字段 |
| G3 | **子项级供方决策** | 组合商品的每个BOM子项独立设置供货模式（指定/最低价优先），逻辑复用单品现有机制 |
| G4 | **优选豁免直通** | 全部BOM子项使用推荐优选供方 → 推品直接豁免审批；存在非优选子项 → 按单品逻辑流入待处理选品走指定审批 |
| G5 | **履约拆单正确** | C端主订单 → 商城后台子订单（按SKU属性拆分）→ 供应链配货单（按供方拆分），三级拆单各层独立追踪 |

### 2.2 不做的事

| 边界 | 说明 |
|:---|:---|
| **不在运营平台展示BOM结构** | 除商品详情页的"组合供货"弹窗外，选品清单、定价推品页、待处理中心均不展示BOM子项明细 |
| **不新增异常类型** | 组合商品的异常处理复用现有六类异常规则（重复数据/利润预警/供应商优化/渠道冲突/成本变动/断供提醒） |
| **不新增审批流** | 子项供方偏离推荐走现有"指定审批"流程，不单独建组合商品审批链路 |
| **不改变C端下单体验** | C端用户按组合SKU整体下单，不感知BOM和拆单逻辑 |
| **不支持集采直发** | 组合商品两种模式均仅支持一件代发履约，不进入集采直发商品池与集采询价链路 |

## 3. 竞品参考

以下竞品分析聚焦**组合商品创建→上架**这条链路，考察三类参照系：通用SaaS（Shopify Bundles / ChannelDock）→ 国内企业采购（得力集实）→ 供方决策模型（Amazon Buy Box）。

### 3.1 竞品对照总结

| 参考系 | 类型 | 核心借鉴 | 本方案差异/增强 |
|:---|:---|:---|:---|
| **Shopify Bundles** | 全球SaaS标准 | 父商品+BOM子项+瓶颈库存的基础模型 | 增加了供方选择层、优选-指定决策链、供货价自动聚合 |
| **ChannelDock** | S2B2C多仓方案 | 多供方+跨渠道的BOM建模可行性 | 增加了人工逐子项指定供方（决策权优先，而非纯自动分配） |
| **得力集实** | 国内B2B采购标杆 | 五步选品上架流程高度吻合，验证两段式分工 | 从"平台自营锁定供方"升级为"多供方择优+审批分流" |
| **Amazon Buy Box** | 供方决策模型 | 推荐方+决策方分离、默认路径顺畅、偏离留痕 | 从"1个SKU选1个供方"扩展为"N个子项各自选供方" |

### 3.2 一句话结论

**BOM基础模型有Shopify验证，多供方跨渠道有ChannelDock实践，国内企业采购流程有得力集实对标，供方决策分权有Amazon Buy Box框架**——本方案是将四者的最佳实践适配到"企业福利多供方组合商品"这个细分场景，核心差异化在于"优选-指定"分级审批链和对运营决策权的尊重。

> 四条参照线的逐项对标明细（做法对照、借鉴与不采纳清单）见附录B。

## 4. 核心设计原则

```
┌─────────────────────────────────────────────────────────────────┐
│                    复杂度边界（最关键的设计决策）                  │
│                                                                 │
│   供应链系统                        商城运营平台                   │
│   ┌─────────────────┐              ┌─────────────────┐          │
│   │ BOM编辑          │              │                  │          │
│   │ 逐子项指供方      │   输出一个    │  当成普通SKU处理  │          │
│   │ 逐子项标优选      │ ──────────→  │  无BOM概念        │          │
│   │                    │  标准SKU    │  无子项概念        │          │
│   │ 聚合计算:         │              │  无多供方概念      │          │
│   │  供货价=Σ子项单价  │              │                  │          │
│   │  库存=min(瓶颈)    │              │  （仅详情页        │          │
│   │  优选逐子项独立判定  │              │   组合供货弹窗     │          │
│   └─────────────────┘              │   可查看/配置BOM）  │          │
│                                    └─────────────────┘          │
│                                                                 │
│   组合商品 = 供应链内部聚合体      组合商品 = 普通SKU            │
└─────────────────────────────────────────────────────────────────┘
```

**一句话**：供应链把多个子项打包成一个标准SKU输出。**核心业务逻辑与校验零改动**（选品、定价、异常分流、上架下架、毛利校验均复用现有规则），**前端展示层按组合类型适配**（列表页商品类型筛选新增"组合套装/营销买赠"、详情页BOM子件清单替换供应商表、供货模式列为组合供货按钮弹窗配置）。

> **核心待解决**：组合商品在整个选品→定价→上架→渠道管理链路中与普通商品处理一致，唯一需要单独设计的是**订单到达供应链系统后的拆单履约配货**——系统需根据BOM快照将组合订单按供方拆分为子发货单，分别发往各子件供应商执行履约，C端以多包裹形式追踪物流。详见 [§9 履约拆单](#9-履约拆单)。

## 5. 供应链侧设计

### 5.1 组合商品创建（新建/编辑弹窗）

在供应链系统·组合商品管理页点击【新建组合商品】（草稿态可再编辑），表单结构如下：

```
Part 1: 组合基本信息
  ├── 组合模式（单选卡片，必填）
  │     ├── ● 组合套装（默认）: 独立SPU，独立售卖。生成全新ZDZH-SPU。
  │     │     子件角色: 主件 + 配件
  │     └── ○ 营销买赠: 挂靠主件ZD-SPU，促销专用。不生成新SPU，主图强制继承主件。
  │           子件角色: 主件 + 赠品
  ├── 组合商品名称 — 商品部自行命名
  └── 品牌/类目/描述 — 复用主件信息，无需手动选择

Part 2: 子件清单（BOM编辑区，商品部/采购部操作）

  ├── 子项选择: 从已入池的供应链SKU中搜索+勾选
  │     └── 约束: 只能选已审核通过且正常供货的供应链SKU
  │
  ├── 每行子项: 子SKU名称 + 编码 + 用量(正整数) + 角色(下拉) + 操作(移除)
  │     ├── 角色: 主件 / 配件 / 赠品（选项随组合模式变化；组合套装=主件/配件，营销买赠=主件/赠品）
  │     │     ├── 主件全局唯一（仅1款主件商品），用量可设置多个（≥1，不再固定为1）；选某行为主件时原主件自动降为配件
  │     │     ├── 配件/赠品可有多个、用量可改
  │     │     └── 允许同一SKU作为不同子项（如主件×1 + 同SKU×2作为配件）
  │     └── 商品信息列展示: 商品名称 + 第二行小字显示供应链SKU · 供应商 · 供货价 · 库存
  │
  └── 操作: [添加子项] [移除子项]
        右侧实时显示"已选N款商品，共M件"（款数按子项去重，件数按用量累加）

Part 3: 组合供货价（只读）
  └── 自动聚合 = Σ(子件供货价 × 用量)，随BOM编辑实时重算，不可手填

Part 4: 主图/详情图
  └── 非必填，不上传则复用主件SKU主图/详情图；营销买赠模式隐藏该区块（强制继承主件）

Part 5: 订单发货备注
  └── 选填，同步至履约与供方配货环节

保存校验: 名称必填、模式必选、至少1个商品、必须有1个主件、所有商品总件数≥2（Σ各子件用量≥2；主件用量可多个，主件×2亦合规）
```

**聚合计算规则**：

| 聚合字段 | 计算规则 | 示例 |
|:---|:---|:---|
| **供货价** | `Σ(子项供方供货价 × 用量)` | 蛋黄酥¥12.5×2+碧螺春¥35×1+坚果¥28×1+包装¥15×1+贺卡¥8×1 = ¥111.00 |
| **库存** | `min(子项库存 ÷ 用量)` 向下取整 | 蛋黄酥500/2=250, 碧螺春50/1=50 → 库存=50 |
| **优选标签** | 逐子项独立判定，不聚合为单一标签。每个子项：有优选标记→运营可采用(豁免)/偏离(审批)；无优选标记→运营自由选择，不受限制 | 蛋黄酥/碧螺春/坚果/包装=有优选，贺卡定制=无优选 → 推品时前4项可采纳豁免，第5项任意选 |
| **供应商展示** | 主供方名 + "等N家" | "食品A等4家" |

### 5.2 组合商品管理列表页

列表页承载组合商品的查询、状态流转与导出，列定义如下：

| 列 | 说明 |
|:---|:---|
| 商品信息 | 组合缩略图 + 组合商品名称 + 供应链SKU（HZZH编码，支持复制）+ 品牌 \| 三级类目 + 组合模式标签（组合套装/营销买赠）+「含N款商品，共M件」 |
| 所属供应链SPU | 组合套装=`ZDZH-`编码；营销买赠=挂靠主件`ZD-`编码 |
| 供应商 | BOM全部子件供方去重聚合，多家显示"供方A 等 N个供应商" |
| 供货价 | 聚合供货价 = Σ(子件供货价 × 用量) |
| 电商参考 | —（组合无独立电商参考价，运营侧以主件电商价作参考） |
| 库存 | 瓶颈库存 = min(子件库存 ÷ 用量) |
| 发货/物流 | — |
| 状态 | 草稿 / 待审批 / 已发布 |
| 供货状态 | 任一子件断供=已失效；否则正常供货 |
| 创建人/创建时间 | 系统记录当前登录用户，时间格式 yyyy-MM-dd HH:mm |
| 操作 | 查看（进详情页）；草稿=提交审批+删除；待审批=撤回；已发布=停用 |

**交互要点**：

| 交互 | 说明 |
|:---|:---|
| 行展开 | 点击展开行显示该组合的BOM子件明细（子件信息/用量/角色/优选供方/电商价/供货状态），展开行提供【优选供应商】标记/切换入口 |
| 筛选 | 关键词（名称/编码）、组合模式、状态 |
| 分页 | 商品图列表标准10条/页，支持每页条数切换与页码跳转 |
| 批量操作 | 批量导出（按当前筛选条件导出组合清单） |

### 5.3 组合商品详情页

详情页页首为组合摘要条（缩略图 + 名称 + 供应链SPU + 品牌 + 类目），主体按Tab组织：

**Tab1 组合信息**：

| 区块 | 内容 |

| 聚合指标 | 聚合供货价（Σ子件供方价×用量）、瓶颈库存（min(子件库存÷用量)）、子件款数、涉及供方数、供货状态 |
| 商品内容 | 组合封面主图集、组合详情图（营销买赠无此区块，强制继承主件） |

**BOM子件清单**（表格，横向滚动，子件信息列与操作列固定）：

| 列 | 说明 |
|:---|:---|
| 子件商品信息 | 缩略图 + 子件名称 + 规格 + 供应链SKU |
| 角色 | 主件 / 配件 / 赠品 |
| 用量 | 正整数 |
| 推荐供应商 | 可切换（BOM锁定后唯一可变项），优选供方带标记 |
| 含税含运一件代发供货价 | 当前推荐供方报价 |
| SKU商品条码 | 子件69条码 |

| 供货状态 | 正常供货 / 已失效 |
| 操作 | 查看子件 |

**BOM结构锁定**：组合创建后子件清单、用量、角色不可修改，仅推荐供应商可切换；切换供方后聚合指标实时重算。待审批状态整页不可编辑。

**Tab2 履约信息**：预留Tab。履约链路上线前展示占位说明（组合订单的履约/拆单信息上线后在此展示），规划方案见§9。

### 5.4 供货价快照

供货价（聚合值）即为组合SKU的对外供货价，每次BOM变更时版本化留存：

| 项目 | 说明 |
|:---|:---|
| 生成时机 | 组合商品提交审批时首次生成；BOM任一子项供方调价/供方替换（切换供方）时生成新版本 |
| 快照内容 | BOM明细（子SKU编码+用量+供方+单价+优选状态）、供货价（聚合值）、快照时间、版本号 |
| 版本规则 | v1 → v2 → ... 逐次递增。已有订单按下单时锁定的快照版本履约 |
| 对已上架组合的影响 | 子项降价→供货价降低自动生效（毛利正向）；子项涨价→供货价升高→走存量巡检→成本变动异常 |

### 5.5 审批与状态机

组合商品审批归**平台审批管理**处理，组合商品管理页不承载审批操作。状态机如下：

```
草稿 ──提交审批──→ 待审批 ──平台审批通过（状态回写）──→ 已发布
 ↑                  │
 │                  └──撤回──→ 草稿
 └──停用────────────────────────┘（已发布 → 停用 → 回到草稿，商品池移出）
```

| 规则 | 说明 |
|:---|:---|
| 提交审批 | 仅草稿可提交；提交后流转至平台审批管理，组合商品管理页该行仅保留"查看/撤回" |
| 撤回 | 仅待审批可撤回；撤回后回到草稿，可继续编辑 |
| 审批通过 | 平台审批管理侧操作，通过后状态回写为已发布，组合进入供应链商品池 |
| 停用 | 仅已发布可停用；停用后回到草稿态（商品池移出、可编辑后重新提交） |
| 删除 | 仅草稿可删除；待审批需先撤回；已发布不可删除（提示先停用） |

### 5.6 子件变更联动机制

组合商品入池上架后，**BOM 结构锁定**（子件清单/用量/角色创建后不可修改），仅每个子件的**供方可变更**（商品部/采购部切换已准入供方）。供方变化或子件侧异常发生时，供应链系统自动重算聚合值并推送至商城运营侧：

```
子件变更类型              供应链侧动作              商城运营侧联动
─────────               ───────────              ────────────
子件供方涨价           重算组合供货价            存量巡检 → 待处理选品（成本变动）
子件供方降价           重算组合供货价            自动生效（毛利正向），无需运营处理
子件断供/下架          组合库存→0              存量巡检 → 待处理选品（断供提醒）
                         组合标记"已失效"          已上架渠道自动不可售
子件优选标签被撤回      重判该子项优选状态        存量巡检 → 待处理选品（供货模式重选）
子件新增更低供方       重判最低价                存量巡检 → 待处理选品（供应商优化）
```

> 子件变更不影响已支付订单的快照版本；运营侧看到的永远是"SKU X的供货价从¥111变为¥120"，不感知BOM内部变化。

### 5.7 两种组合模式的SPU归属与展示差异

两种模式在**定价与渠道流转上完全一致**（都是独立SKU、独立走定价推品、独立商城价/渠道价/毛利），差异仅在 **SPU归属 + 主图 + 在列表中的展示形态**：

| 维度 | 组合套装 | 营销买赠 |
|:---|:---|:---|
| SPU归属 | 生成独立 ZDZH-SPU | 挂靠主件所属 ZD-SPU（不生成新SPU，作为主件SPU下的特殊规格SKU） |
| 主图 | 可自定义，不上传则复用主件主图 | 强制继承主件，不可自定义 |
| 选品清单展示 | 独立SPU行，与单品平权 | 不独立成SPU行，挂在主件SPU展开行下，与普通规格SKU平权，带 `[营销SKU]` 小标签 |
| 渠道商品管理展示 | 独立SPU行 | 同选品清单结构，挂主件SPU下带 `[营销SKU]` 标签 |
| 规格名 | 组合自定义规格（如"标准套装"） | 自动生成：`买赠:主件名+赠品×N` |
| 商品详情页 | 独立详情页 | 无独立详情页；主件SPU详情页头部显示 `[含营销SKU]` 标签，子件绑定区展示营销买赠SKU |
| 主件判定 | 子件中角色=主件（全局唯一，用量≥1） | 同左 |

```
组合套装（独立ZDZH-SPU）:
  供应链商品池:  ZDZH-A00001 [组合套装]  ← 独立SPU行
                   └ HZZH-A00001-001 {标准套装}
  选品清单: 同上，独立SPU行

营销买赠（挂靠主件ZD-SPU）:
  供应链商品池:  ZD-A00001              ← 主件SPU行
                   ├ HZ-A00001-001 {白,常规}       ← 普通规格
                   ├ HZ-A00001-002 {蓝,常规}       ← 普通规格
                   └ HZZH-A00002-001 [营销SKU] 买赠:3M口罩+赠品×3  ← 营销买赠SKU，平权展示
  选品清单: 同上结构
```

> **定价独立性**：营销买赠SKU虽挂靠主件SPU，但其供货价=主件供货价+各赠品供货价之和（赠品有真实定价），商城价/渠道价独立配置，毛利独立计算。在定价推品和渠道发布环节，营销买赠SKU与组合套装SKU、普通单品SKU走完全相同的流程。

### 5.8 子件角色语义

子件角色由商品部在创建组合时根据所选模式标注：

| 角色 | 适用模式 | 含义 | C端展示 |
|:---|:---|:---|:---|
| 主件 | 组合套装 / 营销买赠 | 组合中的主体商品，全局唯一（仅1款），用量可设置多个（≥1） | 作为组合主图/主标题 |
| 配件 | 组合套装 | 搭配进组合的商品 | 可标"搭配/加购"文案 |
| 赠品 | 营销买赠 | 搭送给用户的商品 | 标"赠品"文案 |

> 角色为开放标注字段，V1以上述三种为预置选项。"赠品"在后台与财务口径中仍按其实际供货价处理，C端展示文案与开票口径分离。

## 6. 编码方案适配

基于商城编码方案PRD现行版本（供应链SKU三段式基础码+履约后缀），新增组合商品编码前缀。组合编码与实物/虚拟同构，仅前缀不同：

| 编码层级 | 现有前缀 | 新增前缀 | 示例 |
|:---|:---|:---|:---|
| 供应链SPU | `ZD`=实物 `ZDXN`=虚拟 | `ZDZH`=组合 | `ZDZH-A00001` |
| 供应链SKU | `HZ`=实物 `HZXN`=虚拟 | `HZZH`=组合 | `HZZH-A00001-001` |
| 商城SPU | `S`=实物 `X`=虚拟 | `C`=组合 | `C001A00001` |
| 商城SKU | SPU编码+3位序号 | 同规则 | `C001A00001001` |

> 供应链侧前缀 `ZDZH`/`HZZH` 与已有 `ZDXN`/`HZXN` 同为4位格式，保持一致。商城侧 `C`=组合(Combo)，与 `S`=实物(Shiwu) `X`=虚拟(Xuni) 同为单字母前缀。

组合仅支持一件代发履约：供应链SKU在履约单据上带 `-DF` 后缀（如 `HZZH-A00001-001-DF`），商品维度（列表/详情）展示基础码、隐藏履约后缀，规则与实物商品一致。

子件保留各自原前缀（`S`/`X`），组合商品可混搭实物+虚拟子件：

```
组合商城SPU: C001A00001
  └── 组合商城SKU: C001A00001001
        ├── 子件1: S001A00001001  口罩  (实物)  ×2
        └── 子件2: X001A00001001  服务卡(虚拟)  ×1
```

其余编码规则（字符集、跳过易混淆字符、自增逻辑、编码不可变）沿用现有规范，不做修改。

## 7. 商城运营平台衔接

### 7.1 供应链商品池 — 双池结构下的组合商品

商品池按履约链路分两池：**一件代发商品池 / 集采直发商品池**。组合SKU审批入池后，在一件代发商品池中展示的字段与普通SKU一致，展示形态因**组合模式**不同而有差异：

| 维度 | 说明 |
|:---|:---|
| 池归属 | 组合套装/营销买赠仅支持一件代发 → 天然落一件代发商品池；集采直发商品池不收录组合，其商品类型筛选隐藏"组合套装""营销买赠"两项 |
| SPU行 | 组合套装=独立SPU行（ZDZH编码），商品类型标签"组合套装"；营销买赠=挂主件ZD-SPU展开行下，带 `[营销SKU]` 标签 |
| SKU行规格 | 展示BOM结构摘要：`主件(子件名)×1 + 配件(子件名)×2`（营销买赠含赠品角色） |
| 电商参考 | 组合SKU行显示主件电商价 |
| 同款对比 | 组合/买赠为平台组装SKU，非供方报价行，不参与同款SKU对比 |
| 供货状态 | BOM任一子件断供 → 组合标记"已失效" |
| 操作 | 查看详情（跳商品详情页）、加入选品清单，与普通SKU一致 |

### 7.2 选品清单 — 两种模式展示差异

组合SKU从商品池加入选品清单的操作、校验行为与普通SKU完全一致。展示形态因**组合模式**不同而有差异：

| 环节 | 组合套装 | 营销买赠 |
|:---|:---|:---|
| 加入清单 | 与普通SKU相同 | 与普通SKU相同 |
| 清单展示 | **独立SPU行**（ZDZH编码），与单品平权 | **不独立成SPU行**，挂在主件SPU展开行下，与普通规格SKU平权，带 `[营销SKU]` 小标签 |
| 供货状态 | BOM任一子项断供→已失效 | 同左 |
| 批量配价 | 与普通SKU相同 | 与普通SKU相同 |
| 发起定价推品 | 与普通SKU相同 | 与普通SKU相同（作为独立SKU走校验） |

**不做的事**：清单内不展开BOM结构、不显示优选覆盖率、不新增组合专属状态标签。

### 7.3 定价推品页 — 不动

定价推品配置页零改动。组合SKU进入定价推品页后，所有字段和校验逻辑与普通SKU完全一致：

| 配置项 | 组合SKU表现 |
|:---|:---|
| 渠道选择 | 下拉选择，与普通SKU相同 |
| 销售模式 | 直销/分销，与普通SKU相同 |
| 供货价展示 | 显示聚合供货价¥111.00 |
| 渠道价输入 | 手动/公式，与普通SKU相同 |
| 毛利率计算 | (渠道价-供货价)/渠道价，供货价=聚合值 |
| 供方信息 | 显示聚合后的供方名 |
| 四级校验 | 必填/毛利/商城价，与普通SKU相同 |

**保存时校验与分流**：

```
保存 → 统一校验引擎

  ├── ✅ 直通（生成商城SKU，ON_SHELF）
  │     条件: 所有BOM子项采纳推荐优选供方 + 毛利达标 + 子件映射完整
  │     含义: 逐子项判定：有优选标记的子项均采纳推荐、无优选标记的子项自由选择
  │
  ├── ⚠️ 流入待处理选品中心
  │     ├── 存在子项偏离优选 → 【指定审批待发起】
  │     ├── 某子项优选标签失效 → 【供货模式重选】
  │     ├── 毛利击穿红线 → 【价格异常待处理】
  │     └── 映射缺失 → 【映射补录待处理】
  │
  └── 🔴 阻断（不可提交）
        └── BOM有子项在供应链已失效（前端校验，与普通SKU一致）
```

校验引擎不区分商品是单品还是组合——它只判定供货价、毛利等标准化字段。优选判定在子项级独立执行（逐子项对比商品部标记 vs 运营选择），不聚合成单一标签。

**原子化保存**：组合SKU选了多个渠道时，逐渠道执行校验+分流，A渠道直通成功、B渠道流入待处理，互不影响（与普通SKU一致）。

### 7.4 待处理选品中心 — 不动

组合SKU触发的异常类型和普通SKU完全一致，处理操作完全一致：

| 异常类型 | 触发条件（组合SKU） | 处理操作 |
|:---|:---|:---|
| 重复数据 | 同SKU重复导入 | 忽略删除/重新提交，与普通SKU一致 |
| 利润预警 | 组合毛利率<10% | 修改价格/强制上架，与普通SKU一致 |
| 供应商优化 | 存在更优供方组合 | 一键切换最优/特批申请，与普通SKU一致 |
| 渠道冲突 | 同SKU多渠道冲突 | 商品对比/改价申请/放弃上架，与普通SKU一致 |
| 成本变动 | 供应链通知BOM子项涨价→聚合供货价变更 | 接受并更新/强制下架，与普通SKU一致 |
| 断供提醒 | BOM任一子项断供→组合SKU库存归零/失效 | 确认/移出，与普通SKU一致 |

**关键**：当BOM子项发生变化时，供应链系统重新聚合计算组合SKU的对外属性（供货价、库存、优选标签），然后通过已有的"存量巡检"通道通知运营侧。运营侧看到的永远是"SKU X的供货价从¥111变为¥120"，不关心变化来自BOM子项涨价还是单品涨价。

### 7.5 渠道商品管理 — 两种模式展示差异

组合SKU上架后可售切换、改价、移出操作与普通SKU一致。展示形态因组合模式不同而有差异：

| 维度 | 组合套装 | 营销买赠 |
|:---|:---|:---|
| 列表展示 | **独立SPU行**（C编码），与单品平权 | **挂主件SPU展开行下**，与普通规格SKU平权，带 `[营销SKU]` 标签 |
| 商品类型筛选 | 下拉含"组合套装""营销买赠"两选项 | 同左 |
| 可售切换/改价/移出 | 与普通SKU一致 | 与普通SKU一致 |

### 7.6 运营侧搜索与筛选

组合商品在各列表页的搜索/筛选行为与普通商品一致，不新增专属筛选项：

| 页面 | 搜索字段 | 筛选字段 |
|:---|:---|:---|
| 供应链商品池 | 商品名称 / 型号 / 供应链SKU / 供应链SPU | 商品类型下拉含"组合套装""营销买赠"（仅一件代发商品池） |
| 选品清单 | 商品名称 / SPU编码 | 与普通商品一致 |
| 定价推品页 | 商品名称 | 与普通商品一致 |
| 待处理选品中心 | 商品名称 / 供应链SKU / 供应商 | 问题类型（复用现有7类） |
| 渠道商品管理 | 商品名称 / 商城SPU / 商城SKU | 商品类型下拉含"组合套装""营销买赠" |

> C编码前缀的组合商品在列表中与S编码实物商品平权展示，搜索"组合"关键词可命中商品类型标签。

### 7.7 组合商品生命周期

| 操作 | 行为 | 影响范围 |
|:---|:---|:---|
| 供应链侧删除组合 | 组合SPU标记已删除，商品池不可见 | 已上架渠道→自动下架→待处理选品（断供提醒） |
| 供应链侧切换子件供方 | 重算聚合供货价、生成新快照版本 | 已上架渠道→存量巡检通知；未上架选品→自动刷新 |

| 运营侧强制下架 | 该渠道不可售，可重新上架 | 同普通商品 |
| 组合商品归档 | 供应链侧归档后不可再选入新清单 | 已在途订单按原快照继续履约 |

### 7.8 商品日志

商品详情页Tab3商品日志（详见商品详情页PRD）操作类型新增以下组合商品专属类型：

| 操作类型 | 触发场景 |
|:---|:---|
| 组合商品创建 | 商品部在供应链系统新建组合商品 |
| 组合商品发布 | 运营定价推品后生成组合商城SKU（C编码） |

| 子件断供下架 | BOM子项断供导致组合自动下架，流转至待处理选品 |

> 日志格式、筛选、导出规则与现有商品日志一致，不新增独立日志模块。

## 9. 订单履约 — 三级拆单模型

> **定位说明**：本章为目标态方案。组合订单的拆单履约随履约链路整体上线，一期组合商品上线范围为 创建入池 → 选品推品上架 → 组合供货配置；供应链组合商品详情页「履约信息」TAB已预留入口。

组合商品的订单履约链路采用**三级拆单模型**：C端主订单 → 商城后台子订单 → 供应链配货单，层层拆分，各层职责清晰。

### 9.1 订单拆分全景

```
C端用户下单                                                                      
│  一次性提交购物车，含多个SKU商品                                                   
│  （如：组合套装A ×1 + 单品B ×2 + 虚拟卡券C ×1）                                    
│                                                                                  
▼                                                                                  
┌─────────────────────────────────────────────────────────────┐                    
│                    客户主订单（C端）                           │                    
│  订单号: MO-20260707-00001                                     │                    
│  用户可见，含全部SKU + 总金额 + 多包裹物流追踪                   │                    
└──────────────────────────┬──────────────────────────────────┘                    
                           │                                                      
                           ▼                                                      
              进入商城运营后台（订单中心）                                              
                           │                                                      
         根据 SKU 属性拆分：商品类型 + 供货方归属                                      
                           │                                                      
          ┌────────────────┼────────────────┐                                      
          ▼                ▼                ▼                                      
   ┌──────────┐    ┌──────────┐    ┌──────────┐                                    
   │ 子订单A   │    │ 子订单B   │    │ 子订单C   │                                    
   │ 组合套装A  │    │ 单品B ×2  │    │ 虚拟卡券C │                                    
   │ 金额 ¥99  │    │ 金额 ¥120 │    │ 金额 ¥50  │                                    
   └────┬─────┘    └────┬─────┘    └────┬─────┘                                    
        │               │               │                                          
        │ 组合商品进入    │ 单品直接       │ 虚拟商品                                    
        │ 供应链拆单     │ 匹配供方       │ 即时生效                                    
        │               │               │                                          
        ▼               ▼               ▼                                          
   ┌──────────────────────────────────────────────┐                                 
   │              供应链系统（订单履行）              │                                 
   │                                              │                                 
   │  组合商品子订单A → 查BOM快照 → 按供方拆配货单    │                                 
   │  单品子订单B     → 直接生成配货单               │                                 
   │  虚拟子订单C     → 即时履约，不产生实物配货       │                                 
   └──────────────────────────────────────────────┘                                 
```

**三级拆单层级定义**：

| 层级 | 名称 | 生成位置 | 拆分依据 | 可见方 |
|:---|:---|:---|:---|:---|
| **L1** | 客户主订单 | C端小程序 | 用户一次提交的全部SKU | C端用户 |
| **L2** | 子订单 | 商城后台订单中心 | SKU属性（实物/虚拟/组合）+ 商品类型 | 运营后台 |
| **L3** | 配货单 | 供应链系统 | 组合商品→按BOM供方拆分；单品→直接匹配供方 | 供应链/供应商 |

### 9.2 C端下单 — 库存预占模型

C端用户按组合SKU整体下单，采用 **下单预占 + 支付实扣** 模型：

```
用户提交订单
      │
      ▼
  锁定组合SKU下所有BOM子件库存
      │
      ├── 遍历每个子件：尝试预占 子件库存 ÷ 用量（向下取整）
      │
      ├── ✅ 全部子件预占成功
      │     └── 订单创建成功，组合SKU可售库存实时刷新
      │         各子件预占库存标记为"已锁定"
      │
      └── ❌ 任一子件预占失败（库存不足 / 已失效 / 供方下架）
            └── 整单失败，已预占的子件库存全部释放回滚
                用户端提示："商品库存不足，请稍后再试"
```

| 阶段 | 行为 | 库存状态 |
|:---|:---|:---|
| **下单** | 预占全部子件库存 | 子件库存标记为"已锁定"，可售数 = min(各子件可用库存 ÷ 用量) |
| **支付成功** | 实扣子件库存 | 锁定 → 已售，不可回滚 |
| **支付超时/取消** | 释放预占库存 | 锁定 → 可用，其他订单可继续预占 |
| **任一子件锁失败** | 整单失败 + 已锁库存回滚 | 恢复到下单前状态 |

> **原子性保证**：组合商品下单的子件库存预占是一个原子事务。全部成功或全部回滚，不存在部分子件预占成功、部分失败导致的数据不一致。

C端体验与普通商品一致：

- 商品详情页展示组合封面图 + "含N件商品" + 可展开BOM清单
- 加购/立即购买 → 按组合SKU维度进入订单确认页
- 订单行 = 组合SKU ×1，金额 = 渠道价
- 下单时不感知BOM子件和库存预占逻辑

### 9.3 供应链拆单 — 生成配货单

组合商品订单支付后进入供应链系统，核心动作：**根据 BOM 子件归属的不同供应商，将一条组合订单拆分为多张配货单**，每张配货单对应一个供应商独立履约。

```
                       C端下单
                      组合SKU ×1
                      金额: ¥168.00
                          │
                          ▼
                  订单进入供应链系统
                          │
              查 BOM 快照 v1.0，按供方聚合
                          │
```

**拆单规则**：

| 规则 | 说明 |
|:---|:---|
| **按供方聚合** | 同一供方的多个子项合并到一张配货单 |
| **按仓库聚合** | 同一供方不同仓库 → 可进一步拆分配货单（视WMS能力） |
| **拆单时机** | 订单支付成功 → 进入供应链系统 → 立即拆单生成配货单 |
| **配货单号** | `PH-{供方编码}{序号}`，每张配货单独立追踪 |

| **C端感知** | C端只看到组合订单，拆单和配货单在后台执行，前端展示多包裹物流 |

### 9.5 售后

| 售后场景 | 处理方式 |
|:---|:---|
| **整单退货** | 全部子发货单回退，按原支付方式退款 |
| **整单换货** | 全部子发货单回退 + 重新生成新订单走拆单履约 |
| **仅退款（未发货）** | 全部子发货单取消，全额退款，预占库存释放 |
| **部分子项单独退款** | ❌ 系统不支持自动拆分退款。组合商品作为整体售卖，子项维度售后不可通过系统自动完成 |
| **子项质量问题** | 通过客服人工沟通独立解决（如补发、部分赔付等），不走系统自动退款流程。归责按优选状态：优选供方→供应链侧赔付；非优选供方→运营侧自行承担 |

### 9.6 财务结算

| 维度 | 结算方式 |
|:---|:---|
| 与渠道结算 | 按主订单金额（渠道价），与普通商品一致 |
| 与供应商结算 | 按各子发货单的快照单价分别结算，与普通商品一致 |
| 组合毛利核算 | 渠道价 - Σ(各子项实际结算价)，与供货价聚合逻辑对应 |

## 11. 边界条件与异常处理

| 场景 | 处理方式 |
|:---|:---|
| BOM任一子项在供应链下架 | 组合SKU在商品池自动标记"已失效"，选品清单同步；已上架渠道→自动不可售(供应链)→待处理选品中心(断供提醒) |
| BOM任一子项供方涨价 | 供应链重新聚合供货价→走存量巡检→待处理选品中心(成本变动) |
| BOM任一子项优选标签被撤回 | 供应链重新判定优选标签→若从"优选"变为"非优选"→走存量巡检→待处理选品中心(供货模式重选) |
| 组合SKU下无BOM子项 | 不允许保存，前端校验拦截："请至少添加一个BOM子项" |
| BOM子项用量≤0 | 不允许保存，前端校验拦截 |
| 组合总件数<2 | 不允许保存，前端校验拦截：组合至少需2件商品（Σ子件用量≥2；仅主件×1不合规，主件×2或主件+配件/赠品均合规） |
| BOM子项重复（同一子SKU出现两次） | 同SKU同角色 → 合并为一行累加用量；同SKU不同角色（如主件×1 + 同SKU×2作为配件） → 保留分行，各自独立 |
| 待审批状态下尝试编辑/删除 | 整页不可编辑；删除按钮隐藏，需先撤回 |
| 已发布组合尝试删除 | 不可删除，提示先停用；停用后回到草稿可删除 |
| 弹窗保存时某子项供方已下架 | Toast提示"N个子项关联供应商已下架，请重新选择"，阻止保存 |
| 弹窗保存时某子项OA审批中 | 该子项切换按钮置灰，hover提示"OA审批中"；可保存其他子项配置 |
| 组合供货弹窗打开期间外部数据变更 | 弹窗数据为打开时的快照，关闭弹窗后Tab2自动刷新 |
| 拆单后某子发货单超时未揽收 | 按现有订单超时规则处理，若需整单取消→所有子发货单同步取消 |
| 组合商品售后 | 仅支持整单退货/整单换货，不支持部分子项单独退款 |
| 集采直发链路选组合 | 不支持：集采直发商品池不收录组合套装/营销买赠，集采询价单不可选组合商品 |

## 附录B：竞品详析

### B.1 Shopify Bundles — 最主流的SaaS套装方案

**背景**：Shopify 2023年推出免费原生Bundles App，是目前全球使用最广的电商套装工具。虽面向中小零售而非B2B，但其BOM建模和库存联动机制是行业事实标准。

**组合商品创建→上架链路的做法**：

```
Shopify Bundles                            本方案
══════════════                            ══════

① 创建：选择子商品→生成父商品(Bundle)       ① 创建：选择子SKU→生成组合SKU
    子项数量上限: 30个                           子项数量上限: 暂不限制
    支持固定套装和多件装                          V1仅支持固定BOM

② 定价：Bundle售价=手动填写                  ② 定价：渠道价=手动填写
    子项价格变化→Bundle价格❌不自动更新          供货价=Σ(子项单价×用量)，自动聚合
                                               子项涨价→自动走存量巡检通知

③ 库存：Bundle可售数=min(子项库存)            ③ 库存：=min(子项库存÷用量)，逻辑一致 ✅
    任一子项售罄→Bundle显示售罄                  任一子项断供→组合SKU标记已失效

④ 上架：Bundle作为独立商品上架                 ④ 上架：组合SKU作为独立商品上架，逻辑一致 ✅
    无渠道概念、无审批流                         多渠道独立定价+优选豁免/审批分流

⑤ 履约：订单自动拆为子项SKU                   ⑤ 履约（不在本次范围）：按供方拆单
    子项出库扣减各自库存
```

**关键借鉴与差异**：

| Shopify做法 | 本方案 | 原因 |
|:---|:---|:---|
| Bundle价格不随子项自动更新 | ❌ | B端福利场景成本透明是刚需，供货价必须实时聚合 |
| 瓶颈库存模型 | ✅ 直接采纳 | 行业验证过的做法，防超卖 |
| 订单拆为子项履约 | ✅ 采纳方向 | B端增加了按供方拆单的维度 |
| 无供方概念（单品默认单一供方） | ❌ | B端一品多商是常态，必须加入供方选择层 |
| 无审批流（C端个人决策） | ❌ | B端偏离推荐需组织收口 |

**竞品结论**：Shopify Bundles验证了"父商品+BOM子项+瓶颈库存"这个基础模型。本方案在其之上增加了三个B端必需层：**供方选择**（一品多商）、**优选-指定决策链**（推荐+自由选择+审批）、**供货价自动聚合**（而非手动维护）。

### B.2 ChannelDock — S2B2C多仓多供方套装方案

**背景**：ChannelDock是面向多渠道（Amazon、eBay、Bol.com等）卖家的库存与履约管理平台，原生支持BOM建模的多供方套装。

**组合商品创建→上架链路的做法**：

| 能力 | ChannelDock做法 | 本方案对照 |
|:---|:---|:---|
| **BOM建模** | 定义Bundle → 关联子SKU + 数量比例（如Item A×2, Item B×1） | 一致 ✅ |
| **库存联动** | 子项库存变化→所有关联Bundle跨渠道同步更新 | 一致：子项库存变化→组合SKU库存重算 |
| **多供方** | 子项可来自不同供应商/仓库，系统自动按可用库存分配 | 本方案更进一层：运营可在推品时逐子项选择供方 |
| **跨渠道** | 同一Bundle推送到Amazon、eBay等多个渠道 | 一致：同一组合SKU可推至企业购、航司商城等多个渠道 |
| **供应商指定** | 后台设定优先级规则，系统自动分配 | 本方案支持人工逐子项指定（保留运营决策权） |

**竞品结论**：ChannelDock验证了"多供方+跨渠道+自动库存分配"在S2B2C场景的可行性。它用系统规则自动分配供方（效率优先），本方案在此基础上保留了人工逐子项指定的能力（决策权优先）——这是B端企业福利场景与C端零售的关键差异。

### B.3 得力集实 — 国内企业福利采购的选品上架流程

**背景**：得力集实是得力集团旗下的B2B数字化采购平台，服务86%央企电商集采客户，覆盖员工福利、营销礼品、企业定制等场景，600万+SKU。其"营销洞察→方案策划→选品组合→定制设计→上架交付"五步流程是国内企业福利采购的事实标杆。

**组合商品创建→上架链路的做法**：

```
得力集实 福利礼盒选品上架流程              本方案 五步闭环
═════════════════════════════            ══════════════

① 营销洞察 → 了解客户需求、预算、场景       (运营部/销售部提需求给商品部)
② 方案策划 → 设计礼盒主题、定价策略         ① 组合创建（商品部BOM+供方+优选）

③ 选品组合 → 从商品池选品搭配              ② 选品清单（运营部草稿暂存）
    提供三级定制：浅度/中度/深度                → 对标其浅度定制（标品组合+快速交付）

④ 定制设计 → 视觉、包装、IP联名等          (不在V1范围)
⑤ 上架交付 → 定价、发布到采购平台           ③ 定价推品页 → ④ 待处理选品 → ⑤ 渠道上架
```

**关键借鉴**：

| 得力集实做法 | 本方案采纳 | 说明 |
|:---|:---|:---|
| 三级定制体系（浅/中/深） | V1对标浅度定制 | V1不做包装定制/IP联名，只做标品组合+快速上架 |
| 选品组合阶段确定子项 | ✅ 一致 | 商品部确定BOM子项+用量 |
| 上架交付阶段确定定价 | ✅ 一致 | 运营部确定渠道价+最终供方 |
| 供方在后台锁定 | ❌ 不采纳 | 得力体系内供方=得力自身或指定合作伙伴，不存在"多供方选择"问题；本方案的多供方择优是本系统的差异化能力 |

**竞品结论**：得力集实的五步流程与本方案的五步闭环高度吻合，验证了"商品部组合→运营部定价上架"这个两段式分工在B端企业福利场景的合理性。差距在于：得力的商品和供方是平台自营/提前锁定的，不存在多供方择优和审批分流——这正是本方案要补的差异化能力。

### B.4 Amazon Buy Box — 供方推荐与决策分离模式

已在商品指定供应商方案PRD第3节详述，此处只提炼与组合商品上架链路的映射：

| Buy Box原则 | 组合商品上架链路落地 |
